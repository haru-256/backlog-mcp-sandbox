OVERVIEW

v1 で達成すること

v1 の成果物は、messages を受け取って最終回答を返す同期の Chat API である。 会話の履歴はサーバーに残さない。クライアントが毎回すべての messages を送り、 サーバーは loop 後の messages を返す。この制約が v1 の教材としての価値そのものになる。 履歴を預かってくれる相手がいないので、tool 行を含む配列を自分で運ぶしかなくなり、 messages が表示用データではなくプロトコルであることを、実装として体験できる。

項目完成時の状態
サービスcd v1 && docker compose up で backlog-mcp と chat-v1 が起動する
MCPHost を書く前に initialize と list_tools のスモークが通る
loopCLI と HTTP API が同じ run_tool_loop を呼ぶ
テスト実 LLM と実 MCP なしで、loop の不変条件が検証されている
Chat APIPOST /chat が最終 assistant と全 messages を同期 JSON で返す
履歴クライアントが毎回全 messages を送る。サーバーは保存しない
観測loguru とアクセスログ middleware があり、LOG_FORMAT を切り替えられる
確認画面v1/frontend から同期 Chat を試せる

API

メソッドパス意味
POST/chat受け取った messages で loop を回し、同期 JSON を返す
GET/healthプロセスが応答できることを示す

v1 に入れないもの

DB、Chat セッション、SSE、認証、監査ログ、厳密な error.code と timeout の契約は入れない。 どれも v2 で扱う。省いたものは未完成の印ではなく、一つの loop を正しく読むための余白である。

STEP 2

tool loop を書く

次に作るのは Web アプリではない。一つの発話を受け、LLM と MCP を最終回答まで往復させる関数である。 これが v1 の中心であり、この教材で唯一、ガイドが答えを渡さない部分になる。

境界を先に決める

loop を書き始める前に、loop が何を知らないでよいかを決める。 公式 SDK の型を loop の中で直接触ると、テストのたびに実 MCP と実 LLM が必要になり、 不変条件だけを確かめることができなくなる。そこで SDK を扱う層を二つ用意し、 loop からは次の二つの操作しか見えないようにする。 

# src/chat/agent.py
from typing import Any, Protocol

from openai.types.chat import (
    ChatCompletionAssistantMessageParam,
    ChatCompletionMessageParam,
    ChatCompletionToolParam,
)


class LlmCaller(Protocol):
    """messages と tools を渡すと、assistant 行を 1 つ返す。"""

    async def complete(
        self,
        messages: list[ChatCompletionMessageParam],
        tools: list[ChatCompletionToolParam],
    ) -> ChatCompletionAssistantMessageParam: ...


class McpCaller(Protocol):
    """OpenAI 形式の tools を返し、tool の結果を文字列で返す。"""

    async def list_tools(self) -> list[ChatCompletionToolParam]: ...

    async def call_tool(self, name: str, arguments: dict[str, Any]) -> str: ...

この境界には副産物がある。MCP 接続をいつ開いていつ閉じるかという問題が、 loop の外へ出る。接続の寿命を決める関数と、会話を進める関数が別になる。

SDK を捌く層（全文を渡す）

ここから先の三つのファイルは、SDK の型を必要な形へ写すだけの雑務である。 詰まっても学ぶものがないので全文を渡す。ただし一箇所だけ、後で効く注意がある。 mcp 2.x のフィールドは snake_case である。 古い記事にある inputSchema や structuredContent は、この版では通らない。

# src/chat/mcp_client.py
import json
from typing import Any

from mcp import ClientSession
from mcp.types import TextContent
from openai.types.chat import ChatCompletionToolParam


class BacklogMcp:
    """ClientSession を、loop が使う 2 つの操作だけに絞る。

    mcp SDK の型を扱うのはこのクラスの中だけにする。
    loop 側は OpenAI 形式の tools と、文字列の結果しか知らない。
    """

    def __init__(self, session: ClientSession) -> None:
        self._session: ClientSession = session

    async def list_tools(self) -> list[ChatCompletionToolParam]:
        listed = await self._session.list_tools()
        return [
            {
                "type": "function",
                "function": {
                    "name": tool.name,
                    "description": tool.description or "",
                    "parameters": tool.input_schema,
                },
            }
            for tool in listed.tools
        ]

    async def call_tool(self, name: str, arguments: dict[str, Any]) -> str:
        result = await self._session.call_tool(name, arguments)

        if result.structured_content is not None:
            text = json.dumps(result.structured_content, ensure_ascii=False)
        else:
            blocks = [
                b.text for b in result.content if isinstance(b, TextContent)
            ]
            text = "\n".join(blocks) if blocks else "(tool は内容を返さなかった)"

        # tool 自身のエラーは例外にしない。LLM に見せて自己修正させるのが MCP の設計である。
        # 例外にしてよいのは、tool が見つからない等のプロトコル階層の失敗だけ。
        if result.is_error:
            return f"tool error: {text}"
        return text
# src/chat/llm.py
from openai import AsyncOpenAI
from openai.types.chat import (
    ChatCompletionAssistantMessageParam,
    ChatCompletionMessage,
    ChatCompletionMessageFunctionToolCall,
    ChatCompletionMessageFunctionToolCallParam,
    ChatCompletionMessageParam,
    ChatCompletionToolParam,
)

from chat.settings import Settings


class OpenCodeGoLlm:
    """OpenAI 互換の Chat Completions を、loop が使う 1 つの操作だけに絞る。"""

    def __init__(self, settings: Settings) -> None:
        self._client: AsyncOpenAI = AsyncOpenAI(
            api_key=settings.opencode_go_api_key,
            base_url=settings.opencode_go_base_url,
        )
        self._model: str = settings.opencode_go_model

    async def complete(
        self,
        messages: list[ChatCompletionMessageParam],
        tools: list[ChatCompletionToolParam],
    ) -> ChatCompletionAssistantMessageParam:
        completion = await self._client.chat.completions.create(
            model=self._model,
            messages=messages,
            tools=tools,
        )
        return _to_row(completion.choices[0].message)


def _to_row(message: ChatCompletionMessage) -> ChatCompletionAssistantMessageParam:
    """SDK のモデルを、そのまま次の呼び出しへ渡せる dict にする。

    model_dump() をそのまま使わない。refusal や audio のような None の項目が混ざり、
    互換 API 側で弾かれることがある。必要な項目だけを写す。
    """
    row: ChatCompletionAssistantMessageParam = {
        "role": "assistant",
        "content": message.content,
    }
    if message.tool_calls:
        tool_calls: list[ChatCompletionMessageFunctionToolCallParam] = [
            {
                "id": call.id,
                "type": "function",
                "function": {
                    "name": call.function.name,
                    # arguments は JSON 文字列のまま渡す。ここで dict にすると、
                    # 次の呼び出しで二重にエンコードされる
                    "arguments": call.function.arguments,
                },
            }
            for call in message.tool_calls
            if isinstance(call, ChatCompletionMessageFunctionToolCall)
        ]
        if tool_calls:
            row["tool_calls"] = tool_calls
    return row

接続の寿命を決める層（全文を渡す）

ClientSession は loop の外側で開き、最終回答が出るまで維持する。 その位置がコードとして見えるのが、この関数の役目である。 

# src/chat/agent.py（つづき）
from mcp import ClientSession
from mcp.client.streamable_http import streamable_http_client

from chat.llm import OpenCodeGoLlm
from chat.mcp_client import BacklogMcp
from chat.settings import Settings


async def run_agent(
    messages: list[ChatCompletionMessageParam],
    settings: Settings,
) -> list[ChatCompletionMessageParam]:
    """接続を開き、loop を一度回す。

    接続の寿命を決めるのがこの関数の仕事で、会話を進めるのは run_tool_loop である。
    分けておくと、loop を実 MCP なしでテストできる。
    """
    llm = OpenCodeGoLlm(settings)
    async with streamable_http_client(settings.mcp_server_url) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            return await run_tool_loop(
                messages,
                llm=llm,
                mcp=BacklogMcp(session),
                max_tool_calls=settings.max_tool_calls,
            )

loop 本体

ここはあなたが書く ガイドが渡すのは、シグネチャと不変条件と、通すべきテストだけである。 この関数を写経で通過すると、v1 の目的は達成されない。 詰まったときは 共通の地図の tool loop の原理 に戻る。 
# src/chat/agent.py（つづき）
import json


class ToolCallLimitExceeded(RuntimeError):
    """tool の実行回数が上限に達した。"""


async def run_tool_loop(
    messages: list[ChatCompletionMessageParam],
    *,
    llm: LlmCaller,
    mcp: McpCaller,
    max_tool_calls: int = 10,
) -> list[ChatCompletionMessageParam]:
    """LLM が tool を要求しなくなるまで往復し、更新した messages を返す。

    不変条件:
      - LLM が返した assistant 行は、tool を実行する前に messages へ追加する
      - tool 行の tool_call_id は、対応する assistant.tool_calls[i].id と一致する
      - assistant が複数の tool を要求したら、その全てに tool 行を返す
      - tool_calls を持たない assistant が出たら、そこで終える
      - 実行しようとした tool が通算 max_tool_calls を超えるなら、
        実行せずに ToolCallLimitExceeded を送出する

    引数の messages をそのまま育て、同じ配列を返してよい。
    """
    tools = await mcp.list_tools()
    raise NotImplementedError("ここを書く")

手がかりを二つだけ置く。tool 行の形は {"role": "tool", "tool_call_id": ..., "content": ...} である。 そして call["function"]["arguments"] は JSON 文字列なので、 mcp.call_tool に渡す前に json.loads する。 この二つを取り違えると、LLM は tool の結果を読めないまま二周目に入る。

自分で通すテスト

書けたかどうかは、実 Backlog に問い合わせて目視するのではなく、テストで判定する。 偽の LLM に一度目は tool call、二度目は最終文章を返させ、偽の MCP に決まった結果を返させる。 実 LLM は同じ入力に同じ応答を返さないので、不変条件の検証には使えない。 

uv add --dev pytest anyio
# tests/test_agent.py
import pytest
from typing import Any
from openai.types.chat import (
    ChatCompletionAssistantMessageParam,
    ChatCompletionMessageParam,
    ChatCompletionToolParam,
)

from chat.agent import ToolCallLimitExceeded, run_tool_loop


@pytest.fixture
def anyio_backend():
    return "asyncio"


class FakeLlm:
    """台本どおりに応答し、渡された messages を記録する偽の LLM。"""

    def __init__(self, script: list[ChatCompletionAssistantMessageParam]) -> None:
        self.script = script
        self.seen: list[list[ChatCompletionMessageParam]] = []

    async def complete(
        self,
        messages: list[ChatCompletionMessageParam],
        tools: list[ChatCompletionToolParam],
    ) -> ChatCompletionAssistantMessageParam:
        self.seen.append(list(messages))
        return self.script[len(self.seen) - 1]


class FakeMcp:
    """決まった結果を返し、呼ばれた tool を記録する偽の MCP。"""

    def __init__(self, results: dict[str, str]) -> None:
        self.results = results
        self.calls: list[tuple[str, dict[str, Any]]] = []

    async def list_tools(self) -> list[ChatCompletionToolParam]:
        return [
            {
                "type": "function",
                "function": {
                    "name": name,
                    "description": "",
                    "parameters": {"type": "object"},
                },
            }
            for name in self.results
        ]

    async def call_tool(self, name: str, arguments: dict[str, Any]) -> str:
        self.calls.append((name, arguments))
        return self.results[name]


def tool_call(
    call_id: str, name: str, arguments: str
) -> ChatCompletionAssistantMessageParam:
    return {
        "role": "assistant",
        "content": None,
        "tool_calls": [
            {
                "id": call_id,
                "type": "function",
                "function": {"name": name, "arguments": arguments},
            }
        ],
    }


@pytest.mark.anyio
async def test_tool_result_is_fed_back_to_the_llm():
    llm = FakeLlm([
        tool_call("call_1", "get_issues", '{"statusId[]": [1]}'),
        {"role": "assistant", "content": "未完了の課題は 1 件です。"},
    ])
    mcp = FakeMcp({"get_issues": '[{"id": 42, "summary": "資料を更新する"}]'})

    result = await run_tool_loop(
        [{"role": "user", "content": "未完了課題を教えて"}],
        llm=llm,
        mcp=mcp,
    )

    # LLM が指定した引数で、tool がちょうど一度呼ばれた
    assert mcp.calls == [("get_issues", {"statusId[]": [1]})]

    # 二度目の LLM 呼び出しは、tool を要求した assistant 行と
    # 対応する tool 行の両方を見ている
    second = llm.seen[1]
    assert second[1]["tool_calls"][0]["id"] == "call_1"
    assert second[2]["role"] == "tool"
    assert second[2]["tool_call_id"] == "call_1"

    # 返る messages は 4 行そろっている
    assert [row["role"] for row in result] == ["user", "assistant", "tool", "assistant"]
    assert result[-1]["content"] == "未完了の課題は 1 件です。"

開発中は LOG_FORMAT=human にして、tool 名、引数の要約、所要時間を一行ログで読む。 JSON ログはコンテナから集めるときに効くが、最初の数回は人が追える形の方が loop を観察しやすい。

よくある詰まり方
  • arguments を二重に JSON 化する。文字列のまま messages へ、dict にして call_tool へ
  • tool ごとに MCP 接続を開き直す。initialize と list_tools が毎回走る
  • assistant 行を残さず tool 結果だけを足す。LLM が対応を復元できない
  • inputSchema と書く。mcp 2.x は input_schema である
STEP 2 の合格線 三つのテストが緑になる。 ターミナルから実 Backlog のデータに基づく返答が返る。 ログを読み、どの assistant tool call にどの tool result が対応したかを説明できる。
STEP 3

同じ loop を FastAPI で包む

# src/chat/api.py
from fastapi import FastAPI
from pydantic import BaseModel
from openai.types.chat import ChatCompletionMessageParam

from chat.agent import run_agent
from chat.settings import Settings

app = FastAPI()
settings = Settings()


class ChatRequest(BaseModel):
    messages: list[ChatCompletionMessageParam]


@app.post("/chat")
async def chat(request: ChatRequest):
    messages = await run_agent(list(request.messages), settings)
    return {"message": messages[-1], "messages": messages}


@app.get("/health")
async def health():
    return {"ok": True}

入力の配列をコピーしてから渡しているのは、run_tool_loop が 引数の配列を育てる契約だからである。リクエストのモデルを直接育てないほうが、 後で検証やログを足すときに扱いやすい。

二つ目の発言は全履歴を送る

一つ目のレスポンスを受けたクライアントは、最後の文章だけを覚えるのではない。 tool の行を含む messages 全体を保持し、次の発言に足して送る。

アクセスログをアプリ側でそろえる

Uvicorn のアクセスログは有用だが、tool 呼び出しのログと同じ request ID を持たせにくい。 middleware で request ID、method、path、status、duration を loguru に出し、 レスポンスヘッダにも同じ ID を返す。 

import time
import uuid

from loguru import logger


@app.middleware("http")
async def access_log(request, call_next):
    request_id = request.headers.get("x-request-id") or str(uuid.uuid4())
    started = time.perf_counter()
    response = await call_next(request)
    duration_ms = (time.perf_counter() - started) * 1000
    logger.bind(request_id=request_id).info(
        "access method={} path={} status={} duration_ms={:.1f}",
        request.method,
        request.url.path,
        response.status_code,
        duration_ms,
    )
    response.headers["x-request-id"] = request_id
    return response

v1 では失敗を細かな error.code に正規化しない。 入力不正は FastAPI の validation error に任せ、LLM や MCP の失敗は 短いメッセージと適切な HTTP status に留める。 厳密な error 契約は、状態とストリームも持つ v2 で扱う。

画面には入力欄、送信ボタン、ユーザー発言、最終 assistant 発言、health の状態があれば足りる。 tool call の JSON を常時出す必要はないが、開発中だけ折りたたみで見えるようにしておくと、 messages の実体を観察しやすい。 

import axios from "axios";

const api = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL,
});

export async function postChat(messages: unknown[]) {
  const { data } = await api.post("/chat", { messages });
  return data as { message: unknown; messages: unknown[] };
}
const [messages, setMessages] = useState<Message[]>([]);
const { data: health } = useSWR("/health", () => api.get("/health"));

async function send(content: string) {
  const next = [...messages, { role: "user", content }];
  const response = await postChat(next);
  // サーバーが返した配列で置き換える。tool 行を含む全履歴がここに入っている
  setMessages(response.messages as Message[]);
}

POST の送信は axios で足りる。SWR は /health のような GET の再取得に使い、 Chat の送信までキャッシュの形へ寄せる必要はない。 リロード後も会話を残したければ messages を localStorage に置いてよいが、 それはサーバーセッションではない。サーバーが履歴を預かる設計は v2 の範囲である。 

from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://127.0.0.1:5173", "http://localhost:5173"],
    allow_credentials=False,
    allow_methods=["*"],
    allow_headers=["*"],
)

開発サーバーの origin と FastAPI の origin は異なるため、backend 側で許可する。 任意の origin を許す設定を、そのまま公開環境へ持ち込まない。

STEP 4 の合格線 画面から「未完了課題を教えて」と送ると、実データに基づく返答が見える。 続けて質問すると、クライアントが保持した全 messages が POST される。
WRAP UP

到達点を確かめる

v1 の完成は、画面に返答が出たことではない。次を観測できることである。

  • 公式 Backlog MCP が Compose 上で HTTP 常駐し、initialize と list_tools が通る
  • run_tool_loop の三つのテストが、実 LLM と実 MCP なしで緑になる
  • run_agent が ClientSession を loop の外側で開き、実 MCP を通じて返答する
  • assistant の tool_calls[i].id と tool 行の tool_call_id が対応している
  • POST /chat が CLI と同じ loop を通り、同期 JSON を返す
  • クライアントが全 messages を保持し、サーバーは DB も Chat セッションも持たない
  • loguru とアクセスログ middleware で、一回の要求と tool 実行を追える
  • React の検証画面から二回以上の発言を確認できる

ここまで来れば、Host を「LLM の tool call を MCP の tools/call へ渡し、 結果を正しい messages にして LLM へ戻すプログラム」と説明できる。 同時に、二つの不便さも実感しているはずである。 クライアントが tool 行まで含む全履歴を運ばなければならないこと。 tool を待っているあいだ、利用者には何も見えないこと。

その二つを Host 側へ引き取るのが v2 学習書 である。 Server 側を自分で書くのが v3 学習書 である。 どちらも v1 を終えていることを前提に書いてある。軸が違うので、読む順はどちらからでもよい。
