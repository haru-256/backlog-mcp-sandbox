OVERVIEW

v2 で達成すること

v1 を使っていると、二つの不便さに突き当たる。 クライアントが tool 行まで含む全履歴を運ばなければならないこと。 そして tool を待っているあいだ、利用者には何も見えないことである。 v2 はこの二つを Host 側へ引き取る。引き取ると、v1 では問わずに済んだ問いが生まれる。 いつ保存するのか。失敗したとき何が残るのか。 これが v2 の中心にある問題であり、SSE も監査も、この問いの周辺に配置される。

観点v1v2
履歴の所有者クライアントが毎回 messages 一式を送るHost が PostgreSQL から読み書きする
会話の入口POST /chat に messages を送るセッションを作り、content だけを送る
応答同期 JSONChat 応答は SSE のみ
tool の待ち時間最終回答まで何も見えないstarted / completed / failed を SSE で見せる
失敗の意味短いメッセージと HTTP statustimeout、上限、error.code を契約する
書き込み操作実行できればよい指定した write tool をマスクして監査する

API

メソッドパス成功時の意味
POST/sessions空の Chat セッションを作り、{"id":"<uuid>"} を返す
POST/sessions/{id}/messages発言を受け、SSE で tool 経過と回答を流す
GET/sessions/{id}/messagesordinal 順の保存済み messages を返す
GET/healthHost プロセスの生存を返す

create-or-continue 用の POST /chat は置かない。 未作成のときは Frontend が POST /sessions してから発言する。 セッションの一覧、削除、タイトル変更、メッセージ編集も作らない。 どれも必要になりうる機能だが、保存と SSE の整合を確かめるのに要らない。

v2 に入れないもの

認証の実装、SSE 経過イベントの DB 保存、Redis 等の cache、Kubernetes、承認 UI は入れない。 認証は後から差し込める位置だけを空け、今は Host の本体を観察できる状態に留める。

STEP 1

STEP 2

保存の時点を決める

DB に保存するのは、画面のために短く整えた会話ではない。 次の LLM 呼び出しへそのまま渡せる messages 一式である。 したがって assistant の tool_calls は JSON として残し、 tool 行の tool_call_id も残す。 SSE の経過イベントは保存しない。あれは配信のための一時的な信号であって、会話ではない。

テーブル主な列役割
sessionsid、created_at、updated_atChat セッションの存在と時刻
messagessession_id、ordinal、role、content、tool_calls、tool_call_id、created_atLLM へ再投入できる会話を順序付きで表す
tool_audit_logssession_id、request_id、tool_name、masked_arguments、masked_result、status、started_at、finished_at書き込み tool の説明責任

schema は Alembic の初回 migration として作る。 ローカルの偶然の DB 状態ではなく、どの環境でも同じ tables を再現できるようにするためである。 ordinal はセッション内での順序であり、表示だけでなく LLM に戻す順序として使う。

ここが v2 の中心にある契約

user 行は loop を始める前に保存する。 利用者が発言したという事実を、LLM や MCP やネットワークの失敗で消してはいけない。

これに対して、今回の assistant 行と tool 行は、loop が最終回答へ到達した後でまとめて保存する。 tool を一回実行するたびに保存すると、次の tool や LLM 呼び出しが失敗したとき、 DB には未完結の tool state が残る。次の発言でその配列を読み直すと、 LLM は「tool を要求した assistant 行の途中」から会話を再開することになる。

成功の単位が二つある 「利用者が送信した」が成功したことと、「Host が応答を完結できた」が成功したことは別である。 前者は即座に確定させ、後者は完結した messages だけを確定させる。 こうすると、どこで失敗しても履歴は一貫した状態のままになる。

もう一つ、順序について決めることがある。保存と message.completed の前後関係である。 この教材は保存してから message.completed を送る。 逆にすると、保存に失敗したとき、利用者はすでに確定した回答を見ているのに DB には残っていない、という食い違いが起きる。 先に保存しておけば、message.completed が届いたことは 「この turn は永続化された」と同義になる。

sequenceDiagram participant F as Frontend participant A as Chat API participant D as PostgreSQL participant L as Host loop F->>A: POST /sessions/{id}/messages A->>D: 過去 messages を読む A->>D: user 行を append して commit A-->>F: event: session A->>L: user 行を含む配列で loop alt 最終 assistant まで成功 L-->>A: tool events を経て完結した messages A->>D: この turn の assistant/tool 行を一式保存 A-->>F: event: message.completed else timeout / MCP error / 上限超過 L-->>A: AgentError Note over A,D: この turn の assistant/tool 行は保存しない A-->>F: event: error end A-->>F: event: done 
session_id = 5f...a1、ordinal 順
1  user       content = "未完了課題を教えて"
2  assistant  content = null, tool_calls = [{"id":"call_81", ...}]
3  tool       tool_call_id = "call_81", content = "[{...}]"
4  assistant  content = "未完了の課題は 1 件です。..."
STEP 2 の合格線 user 行は loop 前に残る。 成功した turn は tool 行を含む messages 一式として再読できる。 timeout、MCP error、上限超過の後に、その turn の assistant/tool 行が DB に残っていない。
STEP 3

セッション API

SSE を足す前に、セッションを作る入口と、保存済み履歴を読む入口を固定する。 発言 API が参照する会話の単位を、HTTP の契約として確定させるためである。

存在しない UUID に履歴を要求したときは、HTTP status とともに session_not_found を含む共通 error 形式を返す。 ここではまだ発言を処理しないので、同期 JSON の error body でよい。 SSE 専用なのは Chat 応答だけであり、すべての API をストリームにするわけではない。 

{
  "error": {
    "code": "session_not_found",
    "message": "指定されたセッションは存在しません。",
    "retryable": false,
    "details": {}
  }
}

認証は実装しない。ただし route の dependency から呼べる current_principal のような hook を置く。 今は常に通過する実装とし、後から認証を加えるときに セッション所有者の検証を差し込める境界だけを残す。

認証 hook はアクセス制御ではない 何もしない dependency を置いても、現時点でセッションが保護されるわけではない。 この教材の範囲は、認証を先送りしても route と永続化の責務が崩れない位置を作ることに限る。
STEP 3 の合格線 空のセッションを作り、空の履歴を取得できる。 存在しないセッションは共通 error 形式で失敗する。 POST /chat は存在しない。
STEP 4

SSE で発言する

発言 API は POST /sessions/{id}/messages である。 request body は {"content":"未完了課題を教えて"} だけを持つ。 過去の messages はクライアントから受け取らない。 Host が session_id で DB から読み、今回の user 行を足す。

応答は SSE のみとする。同じ発言に対して同期 JSON を返す別 endpoint は作らない。 二つの応答形式を並べると、Frontend がどちらを正とするか、 エラーの終端をどう解釈するかが二重になる。契約は一つに絞る。

eventdata の要点Frontend がすること
sessionid利用中の Chat セッションを確認する
tool_call.startedname、call_id実行開始を表示する
tool_call.completedname、call_id成功した tool を完了表示にする
tool_call.failedname、call_id、error失敗した tool を区別して表示する
message.deltacontent最終回答の表示バッファへ足す
message.completedrole、contentassistant の最終メッセージを確定する
errorcode、message、retryable、details発言が完了していないことを表示する
done空 objectこの HTTP ストリームを閉じる

LLM の raw な中間状態やプロバイダー固有イベントは SSE に出さない。 診断に必要なら loguru に記録する。 利用者へ公開するのは、会話の進行を理解するために必要な最小集合に留める。

ワイヤ形式と error / event を作る層（全文を渡す）

# src/chat/events.py
import json
from dataclasses import dataclass, field
from typing import Any


@dataclass(frozen=True)
class Event:
    name: str
    data: dict[str, Any] = field(default_factory=dict)

    @staticmethod
    def tool_started(name: str, call_id: str) -> "Event":
        return Event("tool_call.started", {"name": name, "call_id": call_id})

    @staticmethod
    def tool_completed(name: str, call_id: str) -> "Event":
        return Event("tool_call.completed", {"name": name, "call_id": call_id})

    @staticmethod
    def tool_failed(name: str, call_id: str, code: str) -> "Event":
        return Event("tool_call.failed", {"name": name, "call_id": call_id, "error": code})

    @staticmethod
    def message_delta(content: str) -> "Event":
        return Event("message.delta", {"content": content})


def sse(name: str, data: dict[str, Any]) -> str:
    """1 イベントを SSE のワイヤ形式にする。

    SSE は改行でフィールドを区切るため、data の JSON に生の改行を入れられない。
    json.dumps は文字列中の改行を \\n へエスケープするので、indent を付けなければ安全である。
    """
    return f"event: {name}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n"
# src/chat/errors.py
from typing import Any


class AgentError(Exception):
    """利用者へ返せる形が決まっている失敗。"""

    def __init__(
        self,
        code: str,
        message: str,
        *,
        retryable: bool,
        details: dict[str, Any] | None = None,
    ) -> None:
        super().__init__(message)
        self.code = code
        self.message = message
        self.retryable = retryable
        self.details = details or {}

    def to_event_data(self) -> dict[str, Any]:
        """SSE の error イベントに載せる形。"""
        return {
            "code": self.code,
            "message": self.message,
            "retryable": self.retryable,
            "details": self.details,
        }

    def to_body(self) -> dict[str, Any]:
        """同期 JSON API が返す形。"""
        return {"error": self.to_event_data()}


def internal_error() -> AgentError:
    # 予期しない例外の中身を利用者へ出さない。詳細は loguru へ出す
    return AgentError("internal_error", "内部エラーが発生しました。", retryable=False)

loop にイベントを足す

v1 の run_tool_loop は最終的な messages を返すだけだった。 v2 の loop は、同じ往復をしながら、節目を 実際にその処理をした時点で yield する。 まとめて後から流すと、SSE を見せる意味がなくなる。

ここで message.completed を loop から出さないことに注意する。 あれは「保存が終わった」という意味を持つイベントなので、 DB を知らない loop の責務ではない。loop が出すのは tool の経過と、 最終回答を token stream で受け取れる構成なら message.delta までである。 

# src/chat/agent.py
from collections.abc import AsyncIterator


async def agent_events(messages: list[dict], settings: Settings) -> AsyncIterator[Event]:
    """messages を育てながら、経過イベントを yield する。

    v1 の run_tool_loop と同じ不変条件を満たす。加えて:
      - tool を実行する直前に tool_started、成功した直後に tool_completed
      - tool が失敗したら tool_failed を yield してから AgentError を送出する
      - message.completed は yield しない（保存を知らないため）
      - 完結した messages は、引数の配列を育てる形で呼び出し元へ渡す
    """
    async with streamable_http_client(settings.mcp_server_url) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            mcp = BacklogMcp(session, timeout_seconds=settings.mcp_timeout_seconds)
            tools = await mcp.list_tools()
            ...

v1 で書いた loop をここへ移し、tool の前後に yield を挟むだけである。 新しい概念は入らない。timeout については STEP 5 で扱う。

保存と終端を組み立てる

ここはあなたが書く stream_turn は v2 でいちばん間違えやすい関数である。 保存の時点、成功と失敗の分岐、どの経路でも done で閉じること。 この三つが同時に効く場所なので、ガイドは契約とテストだけを置く。 
# src/chat/api/messages.py
from collections.abc import AsyncIterator
from uuid import UUID


async def stream_turn(
    session_id: UUID,
    content: str,
    *,
    store: MessageStore,
    agent: AgentEvents,
) -> AsyncIterator[str]:
    """一回の発言を処理し、SSE の文字列を順に yield する。

    契約:
      - 存在しないセッションなら session_not_found の error を送り、done で閉じる
      - user 行は loop を始める前に保存する
      - 最初に送るのは session イベント
      - loop が出すイベントは、届いた順にそのまま流す
      - loop が完結したら、この turn の assistant/tool 行を保存してから
        message.completed を送る（保存が先。順序を逆にしない）
      - AgentError は error イベントにする。予期しない例外は loguru に出し、
        internal_error として error イベントにする
      - 成功しても失敗しても、最後は必ず done を送る
      - 失敗した turn の assistant/tool 行を DB に残さない
    """
    raise NotImplementedError("ここを書く")

手がかりを一つ置く。agent_events が messages を in-place で育てるなら、 例外で抜けた時点の配列には未完結の行が入っている。 その配列をそのまま保存しないために、 保存する範囲を loop の前に決めておく必要がある。

agent を引数で受けているのは、テストで差し替えるためである。 route 側では agent=lambda rows: agent_events(rows, settings) のように束ねて渡す。 stream_turn が Settings を知らずに済むと、 保存と終端の契約だけを単体で検証できる。

自分で通すテスト

# tests/test_stream_turn.py
from uuid import UUID

import pytest

from chat.errors import AgentError
from chat.events import Event
from chat.api.messages import stream_turn

SESSION_ID = UUID("5f2a7b8e-0000-0000-0000-000000000001")


@pytest.fixture
def anyio_backend():
    return "asyncio"


class FakeStore:
    """messages を配列 1 本で持つ偽の永続化層。"""

    def __init__(self) -> None:
        self.rows: list[dict] = []

    async def exists(self, session_id) -> bool:
        return session_id == SESSION_ID

    async def load(self, session_id) -> list[dict]:
        return [dict(row) for row in self.rows]

    async def append(self, session_id, rows: list[dict]) -> None:
        self.rows.extend(dict(row) for row in rows)


def names(chunks: list[str]) -> list[str]:
    """SSE の文字列から event 名だけを取り出す。"""
    return [chunk.split("\n", 1)[0].removeprefix("event: ") for chunk in chunks]


def succeeding_agent(messages: list[dict], settings=None):
    async def run():
        messages.append({
            "role": "assistant",
            "content": None,
            "tool_calls": [{"id": "call_1", "type": "function",
                            "function": {"name": "get_issues", "arguments": "{}"}}],
        })
        yield Event.tool_started("get_issues", "call_1")
        messages.append({"role": "tool", "tool_call_id": "call_1", "content": "[]"})
        yield Event.tool_completed("get_issues", "call_1")
        messages.append({"role": "assistant", "content": "未完了の課題はありません。"})
    return run()


def failing_agent(messages: list[dict], settings=None):
    async def run():
        messages.append({
            "role": "assistant",
            "content": None,
            "tool_calls": [{"id": "call_1", "type": "function",
                            "function": {"name": "get_issues", "arguments": "{}"}}],
        })
        yield Event.tool_started("get_issues", "call_1")
        yield Event.tool_failed("get_issues", "call_1", "mcp_timeout")
        raise AgentError("mcp_timeout", "MCP がタイムアウトしました。", retryable=True)
    return run()


@pytest.mark.anyio
async def test_successful_turn_saves_before_confirming():

    chunks = [c async for c in stream_turn(
        SESSION_ID, "未完了課題を教えて", store=store, agent=succeeding_agent
    )]

    # 保存は message.completed より前に済んでいる
    assert names(chunks) == [

        "tool_call.started",
        "tool_call.completed",
        "message.completed",
        "done",
    ]
    assert [row["role"] for row in store.rows] == ["user", "assistant", "tool", "assistant"]
    assert store.rows[2]["tool_call_id"] == "call_1"

    assert names(chunks)[-2:] == ["error", "done"]

このテストが守っているもの 三つとも、実際に動かして目視するのが難しい性質である。 失敗した turn に何が残らないかは、失敗を意図的に起こさないと確認できない。 「保存してから確定を送る」順序は、正常系を眺めていても見えない。 SSE が必ず done で閉じることは、閉じ忘れたときに ブラウザがハングして初めて気づく。どれも、後から直すと高くつく。

STEP 5

制限、error 契約、監査、health

外部サービスを二つ含む Host は、成功する経路だけでは説明できない。 LLM が遅い、MCP が応答しない、tool が終わらない、入力が不正である。 これらを区別しないと、Frontend は再試行すべき失敗と、入力を直すべき失敗を判定できない。

時間と回数の上限

設定既定値止める対象
LLM_TIMEOUT_SECONDS60一回の LLM 呼び出しが待ち続けること
MCP_TIMEOUT_SECONDS30一回の MCP 操作が待ち続けること
MAX_TOOL_CALLS10一発言で tool を無限に呼ぶこと

LLM と MCP の timeout を一つにまとめない。呼び出し先も、見るべきログも、 再試行の意味も異なるためである。 tool の回数は assistant メッセージの数ではなく、実行した tool call の数で数える。

実装は自前で wait_for を巻くより、SDK の口を使うほうが素直である。 ClientSession.call_tool は read_timeout_seconds を受け、 AsyncOpenAI は timeout を受ける。 どちらも、超えたら自分の例外を投げるので、それを AgentError に翻訳する。

共通の error 形式

code意味retryable の目安
llm_timeoutLLM 応答待ちが上限を超えたtrue
llm_errorLLM 側の障害、不正応答状況依存
mcp_timeoutMCP 呼び出しが上限を超えたtrue
mcp_errorMCP / Backlog 側の失敗状況依存
max_tool_callstool 回数の上限に達したfalse
session_not_found不明なセッションfalse
validation_errorリクエスト不正false
internal_errorその他false

途中で message.delta を送った後に error が起きることもある。 その内容を最終回答として確定してはいけない。 Frontend は message.completed を受けたときだけ回答を確定し、 error を受けたら未完了の表示を残す。 STEP 2 で保存を先に置いたので、この規則は 「確定した回答は必ず DB にある」という保証と一致する。

書き込み tool の監査

sandbox なので Backlog tool は読み書きとも原則許可する。 ただし WRITE_TOOL_NAMES に登録した tool 名に一致したら、 tool_audit_logs へ記録する。 tool 名は推測で決めず、実際に list_tools が返した名前を確認して設定する。 

# src/chat/audit.py
async def audited_call(mcp, name: str, args: dict, call_id: str, settings, store):
    is_write = name in settings.write_tool_names
    started = utcnow()
    try:
        result = await mcp.call_tool(name, args)
    except Exception as exc:
        if is_write:
            await store.save_audit(
                name, mask(args), mask_error(exc), "error", started, utcnow()
            )
        raise
    if is_write:
        await store.save_audit(
            name, mask(args), mask(result), "ok", started, utcnow()
        )
    return result

マスクの対象は、API key、Bearer token、password に見える key と value である。 課題本文のような一般コンテンツまで無差別に伏せない。 そして、マスク前の値を loguru に出してしまえば DB だけを守っても意味がないので、 ログの引数も同じ関数を通す。

監査は権限管理ではない 監査ログがあっても、書き込みが安全になるわけではない。 これは「何を呼び、何が返ったか」を後から説明できるようにする記録であり、 「呼んでよいか」を判断する仕組みではない。 後者が必要になったら、STEP 3 で空けた認証 hook の位置に足す。

ログ、access log、health

loguru は LOG_FORMAT=human で開発時に読める形を出し、 json で構造化ログを出す。 HTTP middleware は request_id、method、path、status、duration_ms を記録し、 取れる範囲で session_id も bind する。 これで、一回の Chat SSE と、その中の LLM と MCP の記録を同じ request_id で辿れる。

GET /health は必須である。まずはプロセスがリクエストを受けられることを示せばよい。 DB、MCP、LLM の深い依存確認まで health に入れると、 依存先の一時的な失敗で Host 自身の生存判定まで失う。 依存先の状態は別のログと操作で診断する。

STEP 5 の合格線 timeout と tool 上限が、決めた code で終わる。 error の stream は必ず done で閉じる。 write tool の監査行がマスク済みで増える。 /health と、request_id を含む access log を確認できる。
STEP 6

検証用フロント

v2/frontend は完成品の Chat UI ではない。API 契約を目で確かめる検証用の React アプリである。 Compose には入れず、pnpm dev で動かす。 backend の再起動と UI のホットリロードを別々に扱えるので、どちらの問題かを切り分けやすい。

画面の状態取得元意味
session_idPOST /sessions未作成なら発行し、以後の API パスに使う
履歴GET /sessions/{id}/messagesリロード後に成功済み messages を表示する
tool 経過SSE の tool events開始、成功、失敗を一時表示する
回答バッファmessage.delta受信中の最終回答を表示する
回答確定message.completed永続化された assistant メッセージとして固定する

axios と SWR は通常の HTTP に使う。発言の SSE は axios に無理に寄せず、 fetch の ReadableStream を読んで event / data の境界を解析する。 

const response = await fetch(
  `${apiBase}/sessions/${sessionId}/messages`,
  {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Accept: "text/event-stream",
    },
    body: JSON.stringify({ content }),
  },
);

for await (const event of readSseEvents(response.body)) {
  applyChatEvent(event);
}
chunk ごとに JSON.parse しない ネットワークの chunk 境界は、SSE イベントの境界と一致しない。 テキストを buffer に貯め、空行でイベントを区切り、 event: と data: を取り出してから JSON を解析する。 ここを飛ばすと、長い回答のときだけ壊れる不具合になる。

送信ボタンを押したら、user の入力をすぐ画面へ仮表示してよい。 ただし server が user 行を保存することと、Frontend が仮表示することは別の責務である。 stream が error で終わったら、最終 assistant を確定させず、 受信済みの delta と error を「未完了」と分かる形で残す。

STEP 6 の合格線 起動時にセッションを作り、リロード後は履歴 GET で成功済みの会話を戻せる。 画面で tool の開始と終了、回答の進行、error の終端を区別して見られる。 Frontend は pnpm dev でローカル起動し、Compose サービスには含めない。
WRAP UP

到達点を確かめる

v2 の到達点は、Chat UI が一度表示できることではない。 Host が持つ責務を説明でき、観測によってその説明を確かめられることにある。

  • cd v2 && docker compose up で三つのサービスが起動する
  • 同じ session_id を使うと、プロセス再起動後にも保存済み messages を取得できる
  • user 行は loop 前に保存され、失敗した turn の assistant/tool 行は残らない
  • message.completed が届いた回答は、必ず DB にも入っている
  • 保存済み messages には assistant の tool_calls と対応する tool_call_id が含まれる
  • Chat 応答は POST /sessions/{id}/messages の SSE だけで、POST /chat はない
  • SSE は正常時も失敗時も done で終わる
  • LLM 60 秒、MCP 30 秒、tool 10 回の既定制限と、その error.code を確認できる
  • 設定済みの write tool が、秘密らしき値をマスクした監査行を残す
  • /health と request_id を含むログで、Host の生存と一回の要求を追える
  • v2/frontend をローカルの pnpm dev で動かし、SSE を画面で確認できる

ここまで追えれば、会話を覚えることと、SSE を返すことと、MCP を HTTP で呼ぶことが、 同じ「セッション」でも同じ「ストリーム」でもないと区別できる。 その区別ができれば、認証、利用者ごとの所有権、より厳しい監査、再試行方針を足すときも、 どの層へ置くべきかを自分で判断できる。 Server 側を自分で書き、接続とトークンの置き場を設計し直す話は v3 学習書 にある。v2 は前提にしない。
