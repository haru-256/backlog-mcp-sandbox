この教材の読み方

このリポジトリの目的は Backlog を操作することではない。公式 Backlog MCP を使うだけなら、 Claude Desktop や Cursor の MCP 設定に足せば済む。それでも自前の Host を書くのは、 LLM 呼び出しと tool 実行の境界を、自分のコードとして読める場所に置くためである。 したがって完成の基準は「画面に返答が出ること」ではなく、 なぜその messages の並びでなければならないかを説明できることになる。

教材は三段に分かれる。v1 はステートレスな Host で、tool loop だけを扱う。 公式 Backlog MCP を外から使う。v2 は Host の責務を増やす。 会話の永続化、SSE、制限と失敗の契約、監査。公式 MCP は v1 と同じである。 v3 は Server 側を自分で書く。公式を外すのは、スペースと token を Host が持ち、MCP は渡された値で API を叩くためである。 三つの版はコードを共有しない独立したアプリケーションである。 共通ライブラリにまとめると、実装を並べて差分を読むという学習手段が失われるためである。

一方でこの文書は共有する。原理は版によって変わらないからだ。 各版の HTML には、その版でしか意味を持たない手順だけを置く。 読む順序は index、v1 のあと、v2 と v3 はどちらでもよい。 v2 は Host を厚くする軸、v3 は Server を書く軸である。 どちらも v1 を終えていることを前提にし、tool loop を最初から説明し直さない。

ガイドが答えを出さない箇所がある 各版の手順には、青枠で あなたが書く と示した節がある。 そこはガイドが実装を渡さず、満たすべき不変条件と、自分で通せるテストだけを置く。 写経で通過できてしまう部分は、この教材の目的を達成しない。 逆に、SDK の型を捌くだけの雑務コードは全文を渡す。そこで詰まっても得るものがないためである。

なぜ自前の MCP Host を書くのか

IDE の plugin に公式 MCP を追加する方法は、個人の調査には速い。 しかし plugin は、LLM がどの tool を選び、その結果が次の推論にどう渡ったかを、 あなたのコードとして見せない。Host が担う翻訳が、製品の内側に隠れている。

使い方得られるもの見えないもの
IDE plugin すぐに Backlog を操作できる対話 tool 呼び出しの保持、失敗の切り分け、HTTP API としての境界
自前 Host LLM、MCP、クライアントをつなぐ制御を自分で持つ 最初の接続までに書くコードが増える

Host の仕事は仲介である。LLM は「この関数をこの引数で呼びたい」と返す。 MCP は「この tool をこの引数で実行する」というプロトコルで Backlog に届く。 Host は両者のあいだで、tool の定義を渡し、tool call を実行し、結果を会話履歴へ編み戻す。

フレームワークに loop を委譲しない理由 LangChain や LangGraph に任せれば、同じ動作をはるかに短く書ける。 ただし tool result がどこで messages に追加されたかを自分で追う、という目的には合わない。 これは「フレームワークを使うべきでない」という主張ではない。 loop の不変条件を理解した後なら、抽象化を採用しても何が隠れたのかを判断できる。 その判断力を先に作る、という順序の話である。

Host / Client / Server

MCP は HTTP の「クライアントとサーバー」に加え、Host という第三の役割を置く。 三つの語をプロセスと取り違えると、v3 で Server を書いたときに「じゃあ Host は要らなくなるのか」と迷う。 要らなくならない。役割が違うからである。

役割このリポジトリでの実体仕事
Host 各版の backend/（Chat API） ユーザー発話を受け、LLM と MCP Client を回す。tool をいつ呼ぶかは LLM が決める
Client Host プロセス内の MCP SDK Host の一部。MCP Server に tools/list と tools/call を送る
Server v1 / v2 は公式コンテナ。v3 は mcp/ tool の定義と実行。ここでは Backlog の操作
flowchart LR User[User] FE[Frontend] Host[Host_Chat_API] LLM[LLM] Client[MCP_Client] Server[MCP_Server] Backlog[Backlog_API] User --> FE FE --> Host Host --> LLM Host --> Client Client --> Server Server --> Backlog

押さえる点は三つある。版が変わっても、この三つは変わらない。

  • LLM は MCP を知らない。 Host が tool schema を OpenAI 形式に直し、LLM に渡す。
  • LLM は Backlog を知らない。 「課題を取れ」と tool 名を返すだけである。実行するのは Server。
  • Server は会話を持たない。 チャットの履歴は Host（と、v1 / v3 では検証 UI）側にある。

v1 と v2 では Server が公式イメージである。学ぶ対象は Host の責務であって、Backlog API のラッパーではない。 v3 で Server を自分で書くのは、公式 OAuth が 1 サーバー = 1 組織だからである。 複数テナントを一つのプロセスで持つには、スペースと token を Host が持ち、MCP は渡された space と token で API を叩く。 手順は v3 学習書 に置く。

tool loop の原理

典型的な入力は「Backlog の未完了課題を教えて」である。この一文の裏で、次の連鎖が起きる。

sequenceDiagram participant C as 呼び出し元 participant H as Host participant M as Backlog MCP participant L as LLM C->>H: 発話 H->>M: initialize / list_tools H->>L: messages + tool schemas L-->>H: assistant（tool_calls つき） H->>M: tools/call M-->>H: tool result H->>L: assistant 行 + role=tool 行を含む messages L-->>H: assistant（最終回答） H-->>C: 最終回答

ここで最も誤解されやすいのが messages の正体である。 これは画面に会話を描くための表示用データではない。 次の LLM 呼び出しに渡す入力そのものである。 表示だけを考えると tool の行は邪魔に見えるが、LLM にとって tool 行は、 直前に自分が要求した function call への返答であり、省略できない。 

[
  {
    "role": "user",
    "content": "未完了課題を教えて"
  },
  {
    "role": "assistant",
    "content": null,
    "tool_calls": [
      {
        "id": "call_abc",
        "type": "function",
        "function": {
          "name": "get_issues",
          "arguments": "{\"statusId[]\":[1,2,3]}"
        }
      }
    ]
  },
  {
    "role": "tool",
    "tool_call_id": "call_abc",
    "content": "[{\"id\":42,\"summary\":\"資料を更新する\"}]"
  },
  {
    "role": "assistant",
    "content": "未完了の課題は 1 件です。資料を更新する。"
  }
]

2 行目の tool_calls[0].id と 3 行目の tool_call_id が 同じ call_abc であることに注目する。これが対応していないと、 LLM は「その結果がどの依頼に対するものか」を復元できない。 tool の結果だけを文字列として足し、assistant 行を残さない実装は、この対応を壊す。

loop の不変条件 版が変わっても、次の五つは変わらない。v1 でも v2 でも v3 でも、これが崩れていたら実装が間違っている。
  • LLM が返した assistant 行は、tool を実行する前に messages へ追加する
  • tool 行の tool_call_id は、対応する assistant.tool_calls[i].id と一致する
  • assistant が複数の tool を要求したら、その全てに tool 行を返す
  • tool_calls を持たない assistant 応答が出たら、そこで loop を終える
  • 実行した tool の総数には上限を設ける

最後の項目は、tool が連鎖すること自体を禁じるためのものではない。 期待しない loop が外部サービスを無限に呼び続けるのを、Host の責務として止めるためにある。 上限は assistant メッセージの数ではなく、実行した tool call の数で数える。

二種類のセッション

この教材では「セッション」という語が二つの意味で現れる。 同じものとして扱うと、永続化と再接続の設計が必ず破綻する。

名前何を保つか寿命v1v2v3
MCP セッション Streamable HTTP の接続と initialize 後のプロトコル状態 MCP に接続しているあいだ あり あり あり
Chat セッション 会話 ID と会話履歴 会話を再開したい期間 なし あり（PostgreSQL） なし

v1 が「ステートレス」なのは Chat セッションを持たないという意味であり、 毎回の HTTP リクエストで MCP 接続を省くという意味ではない。 Chat セッションを持たない v1 にも MCP セッションは存在する。 v3 の Chat も v1 と同じくステートレスである。増えるのは Chat セッションではなく、 Host がメモリに持つ Backlog 接続である。詳細は v3 学習書 に置く。

逆に v2 でブラウザを再読み込みしたとき、Chat セッションが DB に残っていれば履歴は復元できる。 その事実から MCP 接続も再利用できるとは導けない。 Host は新しい MCP 接続を初期化し、DB から読み直した messages で会話を続ける。

MCP 接続を tool 呼び出しごとに開き直さない ClientSession は loop の外側で開き、最終回答が出るまで維持する。 tool ごとに張り直すと、initialize と list_tools を毎回繰り返すうえ、 接続に紐づく MCP 側の状態も追いにくくなる。

二種類のストリーム

同じ混同が「ストリーム」にも起きる。こちらは v2 で効いてくる。

名前区間運ぶもの
Chat SSE Host → Frontend 発言の進行。tool の開始と終了、最終回答のチャンク、終端イベント
MCP Streamable HTTP Host → Backlog MCP MCP の初期化、tool schema、tool 実行結果

両者はつながっていない。Chat SSE のイベント名を MCP サーバーへ送ることはないし、 MCP の応答をそのままブラウザへ中継することもない。 Host は MCP から受け取った結果を、利用者に見せる意味のある形へ translate してから SSE に載せる。

公式 Backlog MCP を HTTP で常駐させる

v1 と v2 では Backlog MCP をこのリポジトリで実装しない。Nulab が nulab/backlog-mcp-server を公開しており、課題、Wiki、Git、通知の tool 面を こちらで再発明する理由がない。学ぶ対象は Host の責務であって、Backlog API のラッパーではない。

v3 は例外である。公式 OAuth が 1 サーバー = 1 組織であるため、 複数テナントを一つのプロセスで持つには Server を自分で書く。 スペースと token は Host が持ち、MCP は渡された値で API を叩く。 手順は v3 学習書 に置く。 ここでは v1 / v2 が使う公式コンテナの定義だけを示す。

公式サーバーの既定トランスポートは stdio だが、Streamable HTTP も持つ。 この教材は HTTP を選ぶ。stdio ではプロセスの寿命、再起動、標準入出力の監視まで Host が引き受けることになり、 学びたい境界とは別の複雑さが混ざるためである。 Compose 上の常駐サービスにすれば、CLI からも Host コンテナからも同じサーバーに接続でき、 MCP 側の障害を Host のバグと切り分けて調べられる。

各版の compose.yaml に置く backlog-mcp の定義は、v1 と v2 で共通である。 版ごとに違うのは、同じ Compose に何を並べるか（v1 は Host だけ、v2 は Host と PostgreSQL）だけになる。 v3 の Compose は公式イメージを使わず、自前の mcp サービスをビルドする。 

  backlog-mcp:
    image: ghcr.io/nulab/backlog-mcp-server:latest
    environment:
      BACKLOG_DOMAIN: ${BACKLOG_DOMAIN}
      BACKLOG_API_KEY: ${BACKLOG_API_KEY}
      NODE_ENV: development
      MCP_TRANSPORT: http
      MCP_HTTP_HOST: "0.0.0.0"
      MCP_HTTP_PORT: "3333"
      MCP_HTTP_PATH: /mcp
      MCP_HTTP_ALLOWED_HOSTS: backlog-mcp,localhost,127.0.0.1
    ports:
      - "3333:3333"

MCP_HTTP_HOST の 0.0.0.0 は、コンテナの外から接続を受けるための bind 先である。 MCP_HTTP_ALLOWED_HOSTS には Compose 内のサービス名と、ローカル確認に使う host を含める。 ports は、Host を書く前にスモークを通すためにホストへ公開する設定であり、 Compose 内からしか使わなくなったら閉じてよい。

この port を信頼できないネットワークへ出さない Backlog MCP は、Backlog API キーでできる操作をそのまま代行する。 公開する範囲はローカル開発に限る。

Host を書く前にスモークを通す

起動ログを見て「動いていそうだ」で済ませない。MCP クライアントとして initialize と list_tools を実行し、tool 名が返ることを確認する。 ここを先に固定しておくと、後で「課題が取れない」という失敗を Host のバグと混同しなくなる。 

docker compose up -d backlog-mcp
docker compose ps
docker compose logs backlog-mcp
import asyncio

from mcp import ClientSession
from mcp.client.streamable_http import streamable_http_client


async def smoke(url: str) -> None:
    async with streamable_http_client(url) as (read, write):
        async with ClientSession(read, write) as session:
            await session.initialize()
            listed = await session.list_tools()
            print([tool.name for tool in listed.tools])


asyncio.run(smoke("http://127.0.0.1:3333/mcp"))

ここで返る tool 名は、後で二箇所に効いてくる。 一つは LLM に渡す tool schema であり、もう一つは v2 で監査対象にする書き込み系 tool の集合である。 どちらも名前を推測で決めず、実際に list_tools が返した名前を使う。

URL は接続元によって変わる ホストの CLI から見る URL は http://127.0.0.1:3333/mcp だが、 Compose 内の Host コンテナから見る URL は http://backlog-mcp:3333/mcp である。 localhost は常に「いま実行している場所」を指すため、 コンテナ内で localhost:3333 を使うと Backlog MCP ではなく Host 自身を見に行く。

MCP SDK のどの水準を使うか

公式 mcp Python SDK には、接続を扱う水準が二つある。 この教材は低い方を選ぶ。惰性ではなく、見せたいものがあるからである。 

# 高水準。URL 文字列を渡すと Streamable HTTP になり、initialize も内側で走る
from mcp import Client

async with Client(url) as client:
    tools = await client.list_tools()


# 低水準。この教材が使う形
from mcp import ClientSession
from mcp.client.streamable_http import streamable_http_client

async with streamable_http_client(url) as (read, write):
    async with ClientSession(read, write) as session:
        await session.initialize()
        tools = await session.list_tools()

高水準の Client は短く、実務ではこちらでよいことが多い。 それでも低水準を使うのは、initialize という往復が存在すること、 その後に list_tools が来ること、そしてこの接続がどこで開いてどこで閉じるかを、 コード上の位置として見せるためである。MCP セッションの寿命が async with のネストとして目に見える形になる。

これは決断であって、当て推量ではない 低水準 API を使う代償は、行数と、二重の async with の読みにくさである。 得るものは、接続と初期化を自分で並べたという事実だけだ。 その事実が要らなくなったら Client に移してよい。 移すときに何が隠れるかを説明できるなら、この教材の目的は達成されている。

環境と秘密情報

必要なものは Python 3.12 以上、uv、Docker Compose、Node.js、pnpm である。 版はリポジトリ直下の mise.toml に固定してある。 加えて Backlog のドメインと API キー、OpenCode Go の API キーを用意する。

LLM は OpenCode Go の deepseek-v4-flash を既定とし、OpenAI 互換の Chat Completions として openai SDK の base_url を差し替えて呼ぶ。

環境変数用途
BACKLOG_DOMAINBacklog スペース。backlog-mcp コンテナが使う
BACKLOG_API_KEYBacklog API。backlog-mcp コンテナが使う
OPENCODE_GO_API_KEYLLM の認証
OPENCODE_GO_BASE_URL既定は https://opencode.ai/zen/go/v1
OPENCODE_GO_MODEL既定は deepseek-v4-flash
MCP_SERVER_URLHost から Backlog MCP への URL
LOG_FORMAThuman または json

v2 はこれに DATABASE_URL、POSTGRES_PASSWORD、 timeout と tool 上限の設定を足す。詳細は v2.html に置く。 v3 は BACKLOG_DOMAIN / BACKLOG_API_KEY を使わない。 代わりに HOST_PUBLIC_URL を Host が使う。MCP は compose 内部のみで、JWT は置かない。 FRONTEND_PUBLIC_URL、BACKLOG_CLIENT_ID、BACKLOG_CLIENT_SECRET は Host だけが使う。詳細は v3.html に置く。

秘密情報の扱い 値はリポジトリ直下の .envrc を direnv で読み込む。版ごとの .env は必須にしない。 Compose は起動シェルに載った環境変数を参照する。 キーの値を、このガイド、コミット、Issue、PR、ログに書かない。扱うのは環境変数名だけにする。
