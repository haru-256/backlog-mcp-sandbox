v3 学習書
自作 Backlog MCP。接続はチャットの外

v1 で書いた Host の loop は変わらない。変わるのは、向かい側の Server である。 公式 MCP を外し、複数ユーザー・複数スペースのトークンを一つのプロセスに置く。 接続は tool の途中では始まらない。

この文書は v1 を終えていることを前提にする tool loop の不変条件、Host / Client / Server、MCP を HTTP で常駐させる理由は 共通の地図 にある。 run_tool_loop を自分で書き、テストを緑にした経験は v1 学習書 にある。ここではどちらも説明し直さない。 v3 のコードは v1 から import せず、新しく書く。ただし Host の loop の理解は引き継ぐ。 v2 のセッションや SSE は前提にしない。
OVERVIEW

v3 で達成すること

v1 の Server は公式コンテナだった。API キーはスペースにつき一つ、プロセスにつき一つである。 公式 OAuth も 1 サーバー = 1 組織である。Chat の製品として複数テナントを一つの MCP に載せたいとき、 この前提が壊れる。v3 は Server を自分で書き、トークンの置き場を設計し直す。

目的は Backlog 製品を完成させることではない。次の問いに、コードで答えられるようにすることである。

  • MCP の Host / Client / Server は、どのプロセスのどのファイルか
  • LLM は Backlog API を直接呼ばない。なぜ tool を経由するのか
  • 「接続」と「チャット」は、なぜ別の流れなのか
  • 1 つの MCP が複数ユーザー・複数スペースを持つとき、トークンはどこに置くのか
観点v1v3
MCP Server公式イメージ。API キーはプロセスに一つ自前。ユーザーとスペースの組ごとに token
Chat の履歴クライアントが毎回 messages を送る同じ（ステートレス）
Host が知るものMCP の URL加えて user_id / org_id。スペース名は知らない
接続Compose の環境変数チャット外のボタン → OAuth
tool公式の課題・Wiki・Git などlist_connected_spaces と list_issues だけ

API

v3 に入れないもの

PostgreSQL、Chat セッション、SSE、Cursor 向けの Dynamic Client Registration、 課題の作成や更新は入れない。永続化はメモリのみで、再起動すると接続は消える。 省いたものは未完成の印ではなく、Server 側の身元と接続の境界を読むための余白である。

STEP 1

自前の MCP を HTTP で常駐させる

v1 では公式イメージを Compose に置いた。v3 ではその位置を v3/mcp が占める。 トランスポートの判断は同じである。stdio で都度起動せず、Streamable HTTP で常駐させる。 理由は 共通の地図 にある。

SDK は公式 mcp の 2.x を使う。MCPServer であり、 古い記事の FastMCP や Prefect のラッパーではない。 custom_route は認証を通さない。接続画面と health をここに載せる。 /mcp だけが token_verifier を通る。

      HOST_PUBLIC_URL: ${HOST_PUBLIC_URL:-http://localhost:8003}

    ports:
      - "3333:3333"

ALLOWED_HOSTS に mcp:3333 を含める。 Docker の Host ヘッダはサービス名だけとは限らず、ポート付きで届くことがある。 DNS rebinding 保護を入れたまま、Compose 内の Host から届く値を許す。 

# mcp/src/backlog_mcp/server.py
from mcp.server.mcpserver import MCPServer
from mcp.server.transport_security import TransportSecuritySettings


def create_server(settings: Settings) -> MCPServer[None]:
    server = MCPServer(
        name="backlog-mcp",
        instructions="Backlog 課題を、接続済みスペースに対して一覧する。",
    )

    @server.custom_route("/health", methods=["GET"])
    async def health(_request: Request) -> Response:
        return JSONResponse({"ok": True})

    return server


def run() -> None:
    settings = Settings.from_env()
    server = create_server(settings)
    server.run(
        transport="streamable-http",
        host="0.0.0.0",
        port=3333,
        streamable_http_path="/mcp",
        transport_security=TransportSecuritySettings(
            enable_dns_rebinding_protection=True,
            allowed_hosts=settings.allowed_host_list(),
            allowed_origins=settings.allowed_origin_list(),
        ),
    )
この時点では /mcp のスモークを急がない v1 の公式 MCP は API キーだけで list_tools できた。 v3 の /mcp は STEP 2 で JWT を付けてから開く。 先に通すのは認証なしの GET /health である。

curl -sS http://127.0.0.1:3333/health
STEP 1 の合格線 自前イメージが 3333 で応答し、{"ok": true} が返る。 公式 ghcr.io/nulab/backlog-mcp-server は Compose に無い。
STEP 2

身元は Host が JWT で渡す

公式 MCP はプロセスに API キーを一つ持つ。誰が呼んでも同じスペースになる。 v3 は一人の MCP が複数ユーザーを扱う。tool を実行するとき、 「いまの呼び出しは誰か」が Server に届いていなければならない。

その身元はブラウザが MCP に直接渡すのではない。Chat のテナントは Host が知っている。 Host が HS256 の JWT を署名し、MCP が同じ秘密鍵で検証する。 クライアントは自前 Host だけである。Cursor 向けの Dynamic Client Registration は実装しない。

JWT は二種類ある。同じ秘密鍵でも、typ が違う。取り違えると接続画面から tool が呼べてしまう。

typ=connecttyp=mcp
いつ発行するか接続ボタン毎回のチャット
どこへ付けるか/connect?state=/mcp の Bearer
aud付けないMCP の公開 URL
issHost の公開 URLHost の公開 URL
sub / orguser_id / org_id同じ
 
ブラウザ  --connect JWT-->  MCP /connect   --Backlog OAuth-->  そのスペースの token
Host     --mcp JWT------>  MCP /mcp       --保存済み token-->  Backlog API

検証は SDK の token_verifier に載せる。成功したら AccessToken.subject がユーザーになる。 tool 本体は JWT を自分でデコードしない。get_access_token() から subject を取る。 

# mcp/src/backlog_mcp/auth.py
from mcp.server.auth.provider import AccessToken

from .jwt_tokens import TokenError, decode_token


class HostJwtVerifier:
    def __init__(self, secret: str, audience: str, issuer: str) -> None:
        self._secret = secret
        self._audience = audience
        self._issuer = issuer

    async def verify_token(self, token: str) -> AccessToken | None:
        try:
            payload = decode_token(
                token,
                self._secret,
                "mcp",
                audience=self._audience,
                issuer=self._issuer,
            )
        except TokenError:
            return None
        return AccessToken(
            token=token,
            client_id="chat-host",
            scopes=["mcp"],
            subject=payload["sub"],
            claims={"org": payload["org"]},
        )

MCPServer に渡すときは AuthSettings(required_scopes=["mcp"]) を付ける。 connect トークンでは /mcp を開けない。

Host と MCP が同じ秘密鍵を持つ理由 これは第一者の Host だけがクライアントだから成立する。 不特定の IDE から繋ぐ設計にすると、秘密鍵の共有は破綻する。 そのときは Dynamic Client Registration や第三者の認可サーバーが必要になる。 v3 はその問題を解かない。解かないと決めたから、JWT の発行と検証を自分のコードとして読める。
STEP 2 の合格線 typ=mcp の JWT で initialize と list_tools が通る。 typ=connect や改ざんした token では /mcp が拒否する。 /health と /connect は Bearer なしで届く。
STEP 3

接続はチャットの外

「未完了課題を教えて」の途中で OAuth を始めてはならない。 tool の結果に接続 URL を載せると、LLM がそれを会話の一部として扱い、 別ユーザーの画面にリンクが出たり、チャットから認可が始まったりする。 接続は明示的なボタンだけから入る。

sequenceDiagram participant User participant FE as frontend participant Host as backend_api participant MCP as mcp_connect participant Backlog User->>FE: Backlog を接続 FE->>Host: GET /backlog/connect user_id org_id Host->>Host: connect 用 JWT を署名 Host->>MCP: 302 /connect?state=JWT User->>MCP: スペースを入力 Note over MCP: 未登録なら client_id/secret も保存 MCP->>Backlog: 302 OAuth2AccessRequest User->>Backlog: 同意 Backlog->>MCP: GET /callback?code MCP->>Backlog: code を token に交換 MCP->>MCP: connections に user と space を保存 MCP->>FE: 302 ?connected=1

MCP が覚える表は二つある。どちらもメモリであり、再起動で消える。

  1. space_apps — その Backlog スペースの OAuth アプリ。スペースにつき一度
  2. connections — (user_id, domain) → Backlog access token

初めてそのスペースを繋ぐ人は、Backlog に作った OAuth アプリの client_id / client_secret も貼る。 二人目からはスペース名と Backlog ログインだけで足りる。 2 本目のスペースも、同じボタンから同じ /connect に入る。 チャットの tool には connect を置かない。 

# mcp/src/backlog_mcp/store.py

    def __init__(self) -> None:

接続画面は custom_route に載せる。ここは JWT の Bearer を要求しない。 代わりに query の state を typ=connect として検証する。 Host を経由せず /connect を直接開いても、署名が無ければフォームは出ない。

Chat の org と Backlog のスペースは別物 Host が知るのは Chat テナントの org_id である。ユーザーと org は 1:1。 Backlog のスペースドメインは MCP だけが知る。1 ユーザーが複数スペースを接続できる。 tool 引数に organization は置かない。space は Backlog のホスト名である。

callback は認可コードを token に交換し、connections へ書く。 終わったら検証 UI へ 302 する。URL に access token を載せない。 この層のテストは実 Backlog を叩かない。偽の API が exchange_code を返す。

STEP 3 の合格線 接続用 JWT 付きの GET /connect がフォームを返す。 未登録スペースで client を省略すると 400。 callback が (user_id, domain) の接続をメモリに残し、フロントへ connected=1 で戻る。
STEP 4

スペースを解決して課題を返す

ここが v3 の中心である。Host はスペース名を知らない。 JWT の sub からユーザーを特定し、その人が接続したスペースだけを見る。 tool は二つだけにする。

toolすること
list_connected_spacesそのユーザーが OAuth したスペースを返す
list_issues指定スペースの課題を返す。未完了相当（status 1, 2, 3）がデフォルト

list_issues の space は省略できる場合とできない場合がある。 この分岐を間違えると、他人のスペースが見えたり、接続 URL が会話に混ざったりする。

未接続のときに URL を返さない tool は日本語で「画面の接続ボタンから接続してください」と返す。 リンクを付けない。LLM は受け取った文字列を利用者へ中継するだけなので、 ここに URL を置くと、チャットが OAuth の入口になってしまう。

入力の正規化（全文を渡す）

利用者は acme と書くことも、https://acme.backlog.jp/projects/FOO と書くこともある。 比較する前にホスト名へ落とす。これは URL の雑務なので全文を渡す。 

# mcp/src/backlog_mcp/space.py
from urllib.parse import urlparse


def normalize_space_domain(raw: str) -> str:
    """ユーザー入力を Backlog のホスト名に正規化する。"""
    text = raw.strip()
    if not text:
        raise ValueError("space is required")
    if "://" not in text:
        text = f"https://{text}"
    parsed = urlparse(text)
    host = (parsed.netloc or parsed.path).split("/")[0].lower()
    if not host:
        raise ValueError("space is required")
    if "." not in host:
        host = f"{host}.backlog.com"
    return host

STEP 5

Host に user と接続入口を足す

Host の loop は v1 と同じである。 足すのは、MCP を開くときに JWT を付けることと、接続ボタンの 302 だけである。 スペース名も Backlog トークンも Host は持たない。 

# backend/src/chat/agent.py
async def open_mcp_session(
    settings: Settings, user_id: str, org_id: str
) -> AsyncIterator[ClientSession]:
    token = mcp_bearer_token(settings, user_id, org_id)
    async with (
        create_mcp_http_client(headers={"Authorization": f"Bearer {token}"}) as http_client,
        streamable_http_client(settings.mcp_server_url, http_client=http_client) as (read, write),
        ClientSession(read, write) as session,
    ):
        yield session

mcp 2.x の streamable_http_client は http_client= で 既存の HTTP クライアントを受け取る。ここに Authorization を載せる。 v1 のように URL 文字列だけ渡すと、Bearer が付かない。

async def backlog_connect(

    state = sign_token(
        secret=settings.mcp_jwt_secret,
        typ="connect",
        user_id=user_id,
        org_id=org_id,
        issuer=settings.host_public_url,
        ttl_seconds=settings.connect_token_ttl_seconds,
    )
    query = urlencode({"state": state})
    return RedirectResponse(f"{settings.mcp_public_url}/connect?{query}", status_code=302)

POST /chat の本体は v1 と同じ同期 JSON である。 違うのは user_id と org_id が必須になったことだけである。 接続は axios では叩かない。ブラウザのトップレベル GET で 302 を辿らせる。

v1 の画面に、身元入力と接続リンクを足す。チャットの送信はこれまでどおり axios でよい。 接続だけは <a href> のフルページ遷移にする。 axios で /backlog/connect を呼ぶと、302 先の HTML が JSON クライアントに飲まれる。

POST /chat には毎回 user_id と org_id を付ける。 サーバーは履歴を持たないので、messages はクライアントが保持する。v1 と同じである。 

export async function postChat(
  messages: ChatMessage[],
  userId: string,
  orgId: string,
): Promise<ChatResponse> {
  const { data } = await api.post<ChatResponse>("/chat", {
    messages,
    user_id: userId,
    org_id: orgId,
  });
  return data;
}

WRAP UP

到達点を確かめる

v3 の完成は、画面に課題が出たことではない。次を観測できることである。

  • 公式イメージではなく、自前の MCP が Compose 上で HTTP 常駐している
  • /health は認証なし、/mcp は typ=mcp の JWT だけを受け付ける
  • 接続は GET /backlog/connect → MCP の HTML → Backlog OAuth であり、tool 結果に URL が無い
  • space_apps と connections が MCP のメモリにあり、Host は token を持たない
  • 接続 0 / 1 / 2 本以上の分岐と、他人のスペース拒否が、実 Backlog なしのテストで緑になる
  • Host の run_tool_loop は v1 と同じ不変条件を保ったまま、Bearer 付きで MCP を開く
  • 検証 UI の接続はフルページ GET で、チャット POST とは別の入口である

ここまで追えれば、Host が「いつ tool を呼ぶか」を決め、Server が「誰のどのスペースか」を決める、 と説明できる。同じ MCP という語でも、v1 の公式コンテナと v3 の自前プロセスでは、 トークンの置き場が違う。その違いをファイルの位置として指せるようになれば、 永続化や書き込み tool を足すときも、どのプロセスへ置くべきかを自分で判断できる。

Host 側で履歴と SSE を引き取る話は v2 学習書 にある。 v2 と v3 は同じ軸ではない。必要ならどちらから読んでもよい。
